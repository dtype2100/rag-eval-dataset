## 스킬 실행 절차

| 단계 | 수행 내용 | 산출물·통과 기준 |
|---|---|---|
| 1. 사용자 질문 | 어떤 데이터인지, 실제 사용자가 무엇을 찾는지 먼저 질문한다. 형식·언어·예시 질의·검색만/답변까지·시점/권한·원본/청크 제공 가능 여부·수량/예산을 확인한다. 이미 제공한 답은 다시 묻지 않는다. | `intake.json`: 필수 답 또는 명시적 미확인 상태. 답변 없이 문항 생성 금지 |
| 2. 데이터 분석 | 사용자 설명과 실제 파일을 대조한다. 형식, 추출 품질, 표·이미지·음성, 중복, 충돌, 갱신 주기, 언어·주제·권한 분포를 조사한다. 메타데이터 전수 조사와 본문 층화 표본을 구분한다. | `profile.md`: 표본/전체 범위, 누락·손실·분석 불가능 영역 |
| 3. 가능성 판정 | 원본 가독성, 근거 위치 추적, 정답 판정 가능성, 사용 가능한 변환 도구를 확인한다. | `ready`, `conditional`, `blocked`. 조건 미충족이면 문항 생성 대신 필요한 입력/도구를 제시 |
| 4. 평가 설계 | 검색·답변 과업, 관련성, 정답 행동, 언어·난이도·자료 유형별 구성, 샘플 크기와 검토 방식을 결정한다. | `design.md`: 구성표, 제외 범위, 채점 기준, 모집단과 비교 조건 |
| 5. 근거 정규화 | 원본 버전·해시와 위치를 보존한다. 텍스트 범위/표 셀/이미지 영역/음성 시간 구간 등으로 근거를 식별한다. 현재 청크 ID는 별도 연결한다. | `evidence.jsonl`, 원본 인벤토리 및 청크 연결 |
| 6. 파일럿 생성 | 작은 표본으로 사실 조회·비교·여러 근거 결합·수치/조건·해당 과업의 거절/되묻기 문항을 만든다. 근거가 없는 유형을 비율에 맞춰 억지 생성하지 않는다. | `candidates.jsonl`: 질문, 기대 행동, 정답/루브릭, 근거, 유형, 생성 출처 |
| 7. 검증·보완 | 구조·ID·근거 참조 검사와 내용 검토를 나눈다. 독립 검토자가 원문으로 정답과 자연스러움을 확인한다. 실제 질의가 있으면 합성 질의와 구분한다. | 검토 결과·탈락 사유·수정 이력. 해결 안 된 항목은 격리 |
| 8. 확대·동결 | 파일럿의 결함을 고친 뒤 필요한 수만 확대한다. 개발셋과 비공개 최종 평가셋을 출처/중복 집단별로 분리한다. | 버전별 데이터, 체크섬, 구성·커버리지·한계, 검토자 기록. 기존 동결본 덮어쓰기 금지 |
| 9. 측정 연결 | 대상 RAG의 검색 결과 ID/근거와 연결되는지 소규모로 확인한다. 답변 평가라면 출력/인용도 필요하다. | 연결 검증 결과. 측정 실행과 평가셋 생성은 별개이며 실제 시스템 없이는 성능 점수를 주장하지 않음 |

1단계에서 사용자에게 먼저 물을 핵심 질문은 “어떤 자료이며, 실제 사용자는 그 자료에서 무엇을 찾거나 답받으려 하나요?”이다.
이후 누락된 필수 정보만 묶어서 묻는다. 이 저장소를 구현하는 데 실제 사용자 데이터를 요구하지는 않는다.

| 코드/로그/대화 | 파일/행/버전, 시간·화자·스레드, 참조 관계 | 외부 실행이 필요한 정답은 환경 없으면 보류 |
| 스캔/이미지/도표 | 원본 영역과 OCR/시각 판독의 대응, 캡션 손실 | 캡션만 평가하면 텍스트 파생본 평가라고 명시 |

| 벡터만/원본 접근 불가/알 수 없는 바이너리 | 의미와 정답을 확인할 수 있는 연결 자료 필요 | `blocked`: 벡터에서 원문·정답을 복원했다고 가정하지 않음 |

형식 이름만으로 지원을 선언하지 않는다. 실제 추출 도구와 위치 검증이 되는 입력만 `ready`이다.
초기 구현은 에이전트가 기존 도구로 자료를 읽고 문항을 작성하는 스킬과 데이터 검증기다. 모든 형식의 파서·OCR 엔진·생성 API를 새로 개발하지 않는다.

## 모델·청킹에 독립적인 정답

- 정답 근거는 원본의 안정된 근거 ID로 관리한다. 근거 내용이 바뀌면 새 버전·ID를 사용한다.
- 각 `evidence_set`은 답변에 충분한 근거의 AND 묶음이다. 여러 묶음은 OR 대안이다. X와 Y가 모두 필요하면 `[X,Y]`, 같은 사실의 대체 출처가 있으면 `[[A],[B]]`이다.
- 검색 적합성(qrels)은 `relevance_judgments`로 별도 기록한다. “답에 충분한 근거 집합”과 “관련 문서 목록”을 혼동하지 않는다.
- 청킹/임베딩 변경 시 질문·정답·원본 스냅샷은 고정하고, 근거와 새 청크의 매핑만 검토·갱신한다. 매핑이 불가능한 항목은 제외 사유를 공개하며 같은 조건 비교로 포장하지 않는다.
- 모든 관련 근거를 전수 라벨링했다고 가정하지 않는다. 여러 방식의 검색 후보와 원문 검토로 대체 근거를 보완하고, 미판정 결과를 곧바로 오답 처리하지 않는 별도 검토 경로를 둔다.
- `rag-eval` 0.1.0은 대체 근거 집합/다중 모달 표현을 그대로 지원하지 않으므로 자동 평탄화하지 않는다. 손실 없이 표현 가능한 고정 청크·텍스트 하위셋에만 별도 내보내기를 허용한다. 초기 구현에서 변환기는 만들지 않고 연결 조건을 문서화한다.

## 평가 계약과 최소 형식

`dataset.json` 하나로 계약·근거·문항을 묶어 검증하는 표준 라이브러리 CLI를 제공한다.
대규모 생성 중간 파일은 JSONL을 사용할 수 있지만, 초기 검증기는 하나의 JSON 번들을 읽는다.

- `manifest`: schema_version, dataset_id, version, status(draft/frozen), corpus_snapshot, task(retrieval/rag), coverage, limitations, intake, sources, review.
- `intake`: data_description, user_task, query_language, scope, access_policy, external_processing, target_size. 미확인 상태는 draft에 기록하고 동결 시 해소한다.
- `sources`: id, sha256. 실제 데이터 해시와 원본 보관은 생성 실행에서 관리하며 검증기가 원본 진위를 보증하지 않는다.
- `evidence`: id, source_id, modality, locator, content. locator는 모달리티별 구조를 사용하고 content는 원문 발췌 또는 검토된 파생 표현이다.
- `items`: id, query, split(dev/test), leakage_group, query_type, origin(real/synthetic), author, expected_action(retrieve/answer/abstain/clarify), reference_answer, evidence_sets, relevance_judgments, rubric, verification.
- 무응답/되묻기 항목에는 `rationale`에 고정 코퍼스·시점·권한을 기준으로 한 이유와 확인 범위를 기록한다. 특정 검색기에서 안 나왔다는 이유만으로 답 없음 판정 금지.
- `verification`: status(accepted/pending/rejected), reviewer, method. LLM 검토와 사람 검토를 구별하며 자동 점검만으로 정답 검증 완료를 선언하지 않는다.
- 동결에는 전 항목 accepted, 핵심 계약 완비, 구성·한계·검토 기록, 유효한 원본 연결이 필요하다. CLI는 기존 출력 경로를 덮어쓰지 않는다.

독립 검토에서 발견한 빈 조건은 다음처럼 확정한다.

- qrels의 판정 단위는 안정된 근거 ID, 값은 0(무관)/1(부분 관련)/2(직접 관련)이다. 미판정과 0을 구별한다. 청크 단위 지표로 바꿀 때 별도 매핑·판정이 필요하다.
- 검색 전용 `retrieve` 문항은 양성 qrels를 필수로 하고 답변 정답·충분 근거 집합은 요구하지 않는다. RAG `answer` 문항만 정답·루브릭·충분 근거 집합을 필수로 한다.
- 독립 검토는 별도 컨텍스트의 LLM 또는 사람을 허용한다. `review.policy=human-required`인 경우 사람/혼합 검토만 허용한다. 항목별 author/reviewer와 `independent` 선언을 기록하지만 CLI는 실제 독립성이나 정답 진위를 증명하지 못한다.
- 동일 질의·패러프레이즈 집단은 `leakage_group`으로 표시하여 dev/test 교차를 막는다. `split_policy=source-disjoint`면 출처의 `split_group`도 교차 검사한다. `query-disjoint`는 같은 원본 코퍼스에서 서로 다른 질문을 나누는 경우에 사용하며 출처 독립성을 주장하지 않는다.

## 지표와 표본의 한계

- 검색: qrels가 충분한 범위에서 Recall@k/nDCG@k; 결합형 질문에는 충분한 근거 집합 충족률도 보고한다. 빈 정답 집합의 Recall을 임의 정의하지 않는다.
- 답변: 필수 사실·수치 허용 오차·인용·금지 추론·거절/되묻기 행동을 항목별 루브릭으로 평가한다. 정답 문자열의 완전 일치만 강요하지 않는다.
- 모델 비교: 같은 질문·코퍼스·관련성 기준·k·판정자로 비교한다. 임베딩만 비교한다면 다른 설정을 고정한다.
- 전체 평균과 함께 자료 유형·언어·주제·질의 유형별 표본 수와 결과를 공개한다. 한 분야 점수로 모든 분야의 성능을 주장하지 않는다.
- 파일럿 수와 최종 수는 데이터 다양성·목표 차이·예산에 따라 결정한다. 고정된 30개/100개를 신뢰성 보증선으로 삼지 않는다. 최종 측정은 적절한 불확실성을 포함한다.
- 실제 질의가 없으면 업무 대표성이 검증되지 않은 합성 평가셋임을 표시한다. 생성기·검증기 편향은 독립 검토로 줄일 수 있지만 제거를 보장하지 못한다.

## 최초 계획의 부족점과 보완 판정

| 반례 | 질문→분석→자동 생성만으로 충분한가 | 보완 |
|---|---|---|
| 원본 없는 벡터 | 아니오: 정답 의미 확인 불가 | 중단·원본/검증 가능한 라벨 요청 |
| 이미지/표를 텍스트로 강제 변환 | 아니오: 평가 대상 자체가 달라짐 | 모달리티별 근거 위치·손실 공개 |
| 청킹 변경/중복 출처 | 아니오: 정당한 검색 오판 | 원본 근거 ID·AND/OR 집합·qrels 분리 |
| 상충 정책/시점/권한 | 아니오: 정답이 하나로 정해지지 않음 | 유효 범위와 기대 행동을 계약에 포함 |
| 합성 질문만 다량 생성 | 아니오: 실사용 대표성 불명 | 실제 질의 연결·층별 커버리지·한계 보고 |
| 자기 검증 후 동결 | 아니오: 오류가 반복될 수 있음 | 독립 근거 검토·보류 항목 격리 |

보완 후 판정: 다양한 데이터로 확장 가능한 평가셋 구축 절차는 가능하다. “어떤 입력에서도 자동으로 유효한 평가셋을 만든다”는 보장은 여전히 불가능하다.
이를 성공 약속에서 제외하고 지원 범위·조건·불가 사유를 결과에 포함하는 것이 구현의 핵심이다.

## 구현 작업 단위와 검증

- [ ] 1. 계획·검토: `docs/plan.md`, `docs/review.md`; 독립 검토에서 실행을 막는 빈 조건을 보완한다. 공개 저장소를 만들고 계획을 업로드한다.
- [ ] 2. 스킬·계약: `skills/rag-dataset-builder/SKILL.md`, `references/contract.md`, `references/data-types.md`; 입력 질문 선행, 중단, 대체 근거, 손실 공개 시나리오로 행동을 확인한다. 로컬 스킬 포맷 검증도 수행한다.
- [ ] 3. 실행 가능한 검증: 같은 스킬 안의 `scripts/dataset.py`, 합성 예제, `tests/test_dataset.py`; 잘못된 참조·중복 ID·미검토 동결·손실/범위 누락·AND/OR 오염·덮어쓰기·잘못된 JSON을 테스트한다. 표준 라이브러리만 사용한다.
- [ ] 4. 전체 검증·안내: `README.md`, CI, `docs/validation.md`; 깨끗한 체크아웃에서 예제 검증/동결과 전체 테스트를 수행하고 공개 저장소·커밋·Orca 등록을 확인한다. 각 작업 단위별 커밋과 push를 남긴다.

사용 환경 전체 설치나 실제 RAG 평가 실행은 이번 범위가 아니다. 이 저장소를 복제하여 스킬 디렉터리를 설치하는 방법을 제공한다.

## 참고한 1차 자료

- [Ragas: Testset Generation for RAG](https://docs.ragas.io/en/stable/concepts/test_data_generation/rag/): 단일·다중 근거 질의와 도메인에 맞춘 문서 분할·시나리오 설계. 그래프 구현 자체를 의무화하지 않는다.

이 자료들은 설계 근거이며 본 스킬의 범용성이나 유효성을 실증한 자료는 아니다.
